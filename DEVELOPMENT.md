## Development Workflow

The standard development loop for this project:

1. **Analyze** — Use Ghidra to study the WWE '13 binary. Identify a function, kernel import, or behavior.
2. **Plan** — Document what you found in the relevant doc (`Research.md`, issue, or inline comment).
3. **Implement** — Write the hook or stub in C++. Reference the [ReXGlue.md](docs/ReXGlue.md) guide.
4. **Build** — Compile with CMake and Ninja. Check for errors.
5. **Test** — Run the application and observe behavior. Use Tracy or the debug overlay to profile.
6. **Document** — Update comments, docs, and the CHANGELOG.
7. **Commit** — Follow the [commit style](#commit-style) guidelines.

Because this is a recompilation project with a partially-understood binary, much of the work is exploratory. Treat documentation as a first-class artifact — write down what you discover even before you understand it fully.

## Folder Organization

```
wwe13-recompilation/
├── rexglue-sdk/        # ReXGlue SDK (do not modify — submodule)
├── src/                # Project source code (generated + handwritten)
│   ├── generated/      # Auto-generated by rexglue codegen tool (do not edit)
│   ├── hooks/          # REX_HOOK implementations — kernel and game function overrides
│   ├── stubs/          # REX_STUB implementations — placeholder / logging stubs
│   └── wwe13_app.h     # Application class extending rex::ReXApp
├── docs/               # All documentation
├── scripts/            # Utility scripts (Python, PowerShell)
├── cmake/              # Project-specific CMake modules
├── out/                # Build output (git-ignored)
└── ...
```

> `src/generated/` is produced by the `rexglue` codegen tool. Never edit files in that directory — they will be overwritten on the next codegen run. All customization goes in `src/hooks/` or `src/stubs/`.

## Coding Standards

### Language

- C++23 only. The project is compiled with Clang 18+ in strict C++23 mode.
- No MSVC extensions, no GCC extensions, no `#pragma comment(lib, ...)`.
- Use standard library types. Avoid raw pointers where smart pointers or references are cleaner.

### Naming

Follow the conventions already established in the ReXGlue SDK headers:

| Item | Convention | Example |
|------|-----------|---------|
| Types (classes, structs) | `PascalCase` | `PPCContext`, `RuntimeConfig` |
| Functions | `PascalCase` | `OnPreSetup()`, `LoadXexImage()` |
| Local variables | `snake_case` | `guest_addr`, `frame_count` |
| Member variables | `snake_case_` (trailing underscore) | `runtime_`, `kernel_state_` |
| Constants | `kPascalCase` or `SCREAMING_SNAKE_CASE` | `kExLoadedImageNameSize`, `REX_MEMORY_SIZE` |
| Macros | `SCREAMING_SNAKE_CASE` | `REX_HOOK`, `REX_LOAD_U32` |
| Namespaces | `snake_case` | `rex::ppc`, `rex::graphics` |
| Files | `snake_case.cpp` / `snake_case.h` | `wwe13_audio_hooks.cpp` |

### Hook Authoring

When implementing a hook:

```cpp
// Good: use REX_HOOK for auto-marshaled native functions
static u32 MyNativeFunc(u32 arg1, mapped_u32 arg2) {
    // implementation
    return 0;
}
REX_HOOK(sub_82012345, MyNativeFunc);

// Good: use REX_HOOK_RAW when you need direct ctx/base access
REX_HOOK_RAW(sub_82067890) {
    u32 value = REX_LOAD_U32(ctx.r3.u32);
    ctx.r3.u64 = value * 2;
}

// Good: stub with a log message for unimplemented imports
REX_STUB(XInputGetState);

// Good: stub with a specific return value
REX_STUB_RETURN(XMemAlloc, 0);
```

Always add a comment above the hook explaining what the original function does:

```cpp
// XInputGetState: returns the current state of the specified controller.
// Called by WWE '13's input polling loop every frame.
// Registered as an xboxkrnl.exe export at ordinal 0x0049.
REX_STUB(XInputGetState);
```

### Memory Access

Always use the provided macros when reading or writing guest memory. Never compute raw pointers manually:

```cpp
// Correct
u32 value = REX_LOAD_U32(ctx.r3.u32);
REX_STORE_U32(ctx.r4.u32, value + 1);

// Wrong — no byte-swap, no bounds checking
u32 value = *reinterpret_cast<u32*>(base + ctx.r3.u32);
```

For the MMIO region (0x7F000000–0x80000000), use the `REX_MM_*` variants which route through `MMIOHandler`.

### Error Handling

- Use `rex::Result<T>` for functions that can fail.
- Prefer assertions (`REX_ASSERT`) for invariants, not exceptions.
- Log unexpected conditions with `REXCPU_WARN` or `REXKRNL_WARN` rather than silently ignoring them.

### Comments

- All hook implementations must have a comment explaining the original PPC function.
- Public functions must have a Doxygen-style doc comment (`/** ... */`).
- Inline comments should explain *why*, not *what* (the code already shows what).

## Git Workflow

This project uses a simplified version of the ReXGlue SDK's own branching model.

### Branches

| Branch | Purpose |
|--------|---------|
| `main` | Stable, always builds. Tagged releases only. |
| `development` | Active development. All feature work merges here. |
| `feature/<name>` | Feature or research branches. Short-lived. |
| `fix/<name>` | Bug fix branches. |
| `docs/<name>` | Documentation-only changes. |

Never commit directly to `main`. All changes go through `development` via pull request.

### Basic Workflow

```cmd
# Start new work
git checkout development
git pull origin development
git checkout -b feature/audio-xma-decoding

# Work, commit...

# Push and open a pull request
git push -u origin feature/audio-xma-decoding
```

## Commit Style

This project follows the [Conventional Commits](https://www.conventionalcommits.org/) specification.

### Format

```
<type>(<scope>): <subject>

[optional body]

[optional footer]
```

### Types

| Type | When to use |
|------|------------|
| `feat` | A new hook, feature, or capability |
| `fix` | A bug fix |
| `docs` | Documentation only changes |
| `chore` | Build system, tooling, dependency updates |
| `refactor` | Code restructuring without behavior change |
| `perf` | Performance improvements |
| `test` | Adding or modifying tests |
| `stub` | Adding a new stub implementation |
| `research` | Adding research notes or analysis findings |

### Scope

Use the affected subsystem as scope:

`hooks`, `stubs`, `audio`, `input`, `graphics`, `kernel`, `build`, `docs`, `codegen`

### Examples

```
feat(hooks): implement XInputGetState for SDL3 backend
fix(stubs): correct return value for XMemAlloc stub
docs(research): document Xenos command buffer format
chore(build): update rexglue-sdk submodule to 0.8.1
stub(kernel): add REX_STUB for all remaining xboxkrnl exports
research(graphics): document first draw call in startup sequence
```

### Subject Rules

- Use the imperative mood: "add", "fix", "document" — not "added", "fixes", "documents"
- No capital letter at the start
- No period at the end
- Keep under 72 characters

## Documentation Standards

All documentation lives in `docs/` or as root-level Markdown files. Follow these rules:

- Use **Markdown** (`.md`) for all documentation.
- Use **Mermaid** (fenced code blocks with ` ```mermaid `) for diagrams.
- Use **tables** to present structured information (comparisons, lists of items with multiple properties).
- Use **code blocks** with a language identifier for all code examples.
- Keep line length under 120 characters for prose.
- Use relative links between documents (e.g. `[ReXGlue](docs/ReXGlue.md)`).
- Every new concept should be explained in [docs/Glossary.md](docs/Glossary.md).
- Use callout blockquotes for important notes:

```markdown
> **Note:** This only applies to the D3D12 backend.
> **Warning:** Do not modify files in `src/generated/`.
> **Tip:** Use `ninja -j4` to limit parallel jobs on slower machines.
```

## Issue Tracking

Use GitHub Issues to track work. Follow the issue templates provided.

### Labels

| Label | Meaning |
|-------|---------|
| `bug` | Something is broken |
| `enhancement` | New feature or improvement |
| `research` | Reverse engineering investigation |
| `stub` | Kernel or game function needs implementation |
| `documentation` | Documentation gap or error |
| `good first issue` | Suitable for new contributors |
| `blocked` | Waiting on external dependency or information |

### Creating a Good Issue

For a stub that needs implementing, include:
- The function name and ordinal (if known)
- Which module exports it (xboxkrnl.exe, xam.xex, etc.)
- What it does (from Xbox 360 SDK docs or Xenia's implementation)
- Any context about how WWE '13 calls it (call frequency, arguments)

## Code Review Process

All pull requests require at least one review before merging to `development`.

### Author Checklist

- [ ] Code compiles in Debug and Release configurations
- [ ] No new compiler warnings
- [ ] All new hooks have comments explaining the original function
- [ ] CHANGELOG.md is updated
- [ ] Documentation is updated if the change affects public behavior
- [ ] Commit messages follow the [Conventional Commits](#commit-style) format

### Reviewer Checklist

- [ ] The implementation is correct for the known behavior of the function
- [ ] Memory access uses `REX_LOAD_*` / `REX_STORE_*` macros correctly
- [ ] No raw pointer arithmetic into guest memory
- [ ] New stubs log appropriately — not too verbose, not silent
- [ ] No unnecessary dependencies added to the build

## Testing Strategy

This project does not yet have automated game-level tests. Testing is currently manual and observational.

### Manual Testing

For each phase, define a clear set of observable outcomes:
- Phase 4: application launches without immediate crash; startup log shows no missing symbols
- Phase 5: a frame is rendered; at minimum a solid color appears in the window
- Phase 6: audio device opens; at minimum no crash during audio initialization
- Phase 7: controller input is read; at minimum the main menu responds to navigation

### ReXGlue PPC Tests

The ReXGlue SDK includes a PPC instruction test pipeline. These tests verify that individual PPC instructions are translated correctly by the codegen. Enable them with:

```cmd
cmake --preset win-amd64 -S rexglue-sdk -DREXGLUE_BUILD_TESTS=ON
cmake --build rexglue-sdk/out/build/win-amd64 --config Debug
ctest --test-dir rexglue-sdk/out/build/win-amd64 --preset win-amd64-debug
```

### Logging as Verification

The SDK's logging system (`REXCPU_DEBUG`, `REXKRNL_WARN`, etc.) is your primary debugging tool in the early phases. Configure the debug overlay and log capture sink in the `ReXApp` subclass to surface log output in the window.

## Build Process

### Quick Reference

```cmd
# Configure (once per new clone or after CMakeLists changes)
cmake --preset win-amd64

# Build Debug
cmake --build out/build/win-amd64 --config Debug

# Build Release
cmake --build out/build/win-amd64 --config Release

# Build RelWithDebInfo (optimized with debug symbols — best for profiling)
cmake --build out/build/win-amd64 --config RelWithDebInfo
```

### Output Location

| Config | Path |
|--------|------|
| Debug | `out/win-amd64/Debug/` |
| Release | `out/win-amd64/Release/` |
| RelWithDebInfo | `out/win-amd64/RelWithDebInfo/` |

### Incremental Builds

CMake and Ninja handle incremental builds automatically. After changing a `.cpp` file, just run the `--build` command again — only changed files will recompile.

### Clean Build

If you encounter unexplainable build errors, delete the build directory and reconfigure:

```cmd
rmdir /s /q out\build\win-amd64
cmake --preset win-amd64
cmake --build out/build/win-amd64 --config Debug
```

### Build Options

These CMake options can be passed at configure time:

| Option | Default | Description |
|--------|---------|-------------|
| `REXGLUE_ENABLE_TRACY` | `ON` | Tracy profiler (compiled out in Release) |
| `REXGLUE_ENABLE_PERF_COUNTERS` | `ON` | Lightweight perf counter overlay |
| `REXGLUE_ENABLE_SANITIZERS` | `OFF` | UBSan (do not combine with ASan) |
| `REXGLUE_USE_D3D12` | `ON` (Windows) | Direct3D 12 backend |
| `REXGLUE_USE_VULKAN` | `OFF` (Windows) | Vulkan backend |

Example: enable Vulkan on Windows for cross-platform testing:

```cmd
cmake --preset win-amd64 -DREXGLUE_USE_D3D12=OFF -DREXGLUE_USE_VULKAN=ON
```

For a complete build guide including debugging and profiling, see [docs/BuildGuide.md](docs/BuildGuide.md).
